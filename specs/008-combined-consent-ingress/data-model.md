# Data Model: Combined Consent and Pet Ingress with a Single Signature

**Feature**: 008-combined-consent-ingress | **Date**: 2026-11-10

One migration (`0007_registro_combinado.sql`), no new tables. Column names follow the existing Spanish naming.

## Changes to existing tables

### `dbo.sesiones_firma`

| Change | Detail |
|---|---|
| `CK_sesiones_firma_tipo` | Widened to `('consentimiento', 'ingreso', 'entrega', 'ingreso_combinado')` (drop and re-add, as migration 0006 did) |

No new column. The `payload` and `resultado` JSON shapes for the new type are in [contracts/api-signing-session-combined.md](contracts/api-signing-session-combined.md).

### `dbo.consentimientos`

| Column | Type | Notes |
|---|---|---|
| `firma_grupo_id` | `NVARCHAR(40) NULL` | Same value as on the visit created by the same combined registration. `NULL` for every record that did not come from a combined flow, including all history. |

`legal_hashes` (existing JSON) gains the key `firma_unica` for combined consents. No other consent column changes. `firma_sesion_id` keeps pointing to the signing session for digital signings.

### `dbo.visitas`

| Column | Type | Notes |
|---|---|---|
| `firma_grupo_id` | `NVARCHAR(40) NULL` | See above. |
| `firma_unica_hash` | `CHAR(64) NULL` | SHA-256 of the single-signature clause shown to the tutor; `NULL` for visits not created in a combined flow. |

The visit keeps using `firma_ingreso_tipo` / `firma_ingreso_data` / `firma_tienda_ingreso` for the signature pair; in a combined flow these hold the same images as the consent's `firma` / `firma_tienda`. Existing columns for the intake acceptance (`clausulas_respuesta_condiciones`, `condiciones_version`, `condiciones_hash`, `condiciones_con_recargos`) are used unchanged.

## Spec entities mapped to storage

| Spec entity | Stored as |
|---|---|
| Combined Signing | A `sesiones_firma` row of type `ingreso_combinado` (digital) and the shared `firma_grupo_id` on both resulting records (digital and paper) |
| Consent Record | `dbo.consentimientos` row (existing), plus `firma_grupo_id` |
| Visit (Ficha de Ingreso) | `dbo.visitas` row (existing) with its `visita_cargos` for upfront treatments, plus `firma_grupo_id`, `firma_unica_hash` |
| Signature Pair | The same two PNG data URLs written to both rows (no separate store) |
| Entry Summary | The `entrada` object inside the session `payload`; after saving it is the visit row itself |

## State and lifecycle

**Signing session (`ingreso_combinado`)** uses the existing states `esperando → conectada → firmada → (consumida = cancelada)` / `expirada` / `cancelada`, with two differences from the other types (research R-5):

```text
esperando --tablet opens--> conectada --tablet submits--> firmada (expira_en = now + 10 min)
firmada --registration saved (same transaction)--> cancelada (payload, resultado wiped)
firmada --expira_en passed--> expirada (payload, resultado wiped)
esperando | conectada | firmada --staff closes modal / tablet cancels--> cancelada (wiped)
```

**Outcome of a registration** (research R-6):

| Result code | Rows written |
|---|---|
| `admitido` | client and pet upserted, consent `aceptado`, visit `ingresada` + its upfront treatment charges |
| `solo_consentimiento` | client and pet upserted, consent `aceptado`, no visit |
| `consentimiento_rechazado` | client and pet upserted, consent `rechazado`, no visit |
| (privacy refused) | nothing written; the endpoint answers 422 and staff is told |

All rows of one registration are written in one transaction or none are.

## Validation rules

- `firma_grupo_id` is generated by the server (`uid("fgr")`), never accepted from the client.
- A digital registration requires a session of type `ingreso_combinado` in state `firmada`, not expired; the submitted client, pet, `entrada`, decisions and legal hashes must equal the session snapshot (409 otherwise).
- A digital registration with `terminos = acepta` requires both signature images; a paper registration requires the explicit confirmation flag.
- The visit rules of `POST /api/visitas` apply unchanged: estimated duration > 0 when the conditions carry surcharges, and each upfront treatment needs description, amount > 0 and a valid origin.
- A pet that already has an open (`ingresada`) visit cannot be registered through this path (FR-019; checked inside the transaction for pets that already exist).
- `autoriza_fotos_redes` on the visit is taken from the photos decision of the same signing and defaults to `false` (constitution III and V).

## Privacy and ARCO+

No new table and no new personal field. Client and pet data pending signature exist only inside the session `payload` and are wiped at any terminal state (research R-3, R-5). The existing client export and suppression already cover `consentimientos` and `visitas`, so the two new id/hash columns need no change there; suppression of a client removes both linked records as it does today.
